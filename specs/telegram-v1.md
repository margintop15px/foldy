# Foldy messaging specification — Telegram first

Status: specified, not implemented. T01 follows core chunk 06; T02 follows T01 and core chunk 08. Commands and test paths below are target interfaces until their owning chunk is implemented. The first deliverable is this contract and the accompanying roadmap changes, with no runtime implementation.

This extends the [core behavioral contract](foldy-v1.md). [Implementation chunks](implementation.md#t01--telegram-conversation) define the build order and evidence gates. Markdown requirements and explicit scenarios are the executable specification; no new specification language or test framework is introduced.

Decision (2026-09-12): use CopilotKit Channels as the messaging foundation, with its direct Telegram adapter first. Later messenger integrations will use the same Channels boundary and Foldy operations, each with its own provider contract and acceptance checks. Only Telegram is enabled in T01/T02.

## 1. Scope and connection

**TG-01 — Optional communication.** One personal bot connects one private user chat to one canonical watched root. Telegram is off by default. Local inference, document extraction, source storage, and application authority remain governed by V1-01–03 and ACT-01–07. Enabling and pairing Telegram authorizes useful result messages, questions, answers, and delivery of Foldy-generated artifacts to that chat. This includes folder-derived information in those messages and artifacts. Original source attachments, internal state, arbitrary file uploads, and messages to other recipients are outside this authorization.

CopilotKit Channels and CopilotRuntime run inside the foreground `watch` process. Use `@copilotkit/channels/telegram` in direct long-polling mode. The SDK owns the Telegram connection and native rendering; Foldy does not build a second polling loop or messaging-provider framework. CopilotKit Intelligence is an accepted external service dependency for the SDK lifecycle, even with a direct adapter. There is no hosted Foldy service, public HTTP endpoint, Mini App, or background-service installer. `scan` does not start Channels. Telegram or Intelligence failures do not prevent local observation or processing, and neither service enables remote inference. TG-14 defines the SDK and data boundary.

**TG-02 — Pairing and identity.** The user creates a dedicated personal bot through BotFather and supplies its token through `FOLDY_TELEGRAM_BOT_TOKEN` before starting `watch`, together with the CopilotKit configuration in TG-14. Credentials alone do not pair a recipient. The terminal control `telegram pair` displays what may be sent and issues an unpredictable, single-use private-chat start link expiring after ten minutes. Issuing a replacement invalidates the previous link. A valid `/start` consumes the pairing secret and binds the bot identity, numeric Telegram user and chat identities, and canonical root. Verify both sender and private chat for every subsequent message and callback; usernames and message text are not identity. Use the SDK's identity hook to map only the paired provider actor to Foldy's owner; the pairing handler is the sole exception for an unpaired actor with a valid start secret. The SDK's unrestricted platform-identity default does not authorize access to Foldy.

Keep bot and Intelligence credentials out of SQLite, model context, output, and logs, including SDK logs. Store only a verifier for the pairing secret and never retain the raw pairing command in received-message history or SDK callback/transcript state. Display the pairing link only in the initiating terminal. Before any folder data is sent, verify the configured token still identifies the bound bot. A mismatched token, competing poller, or pre-existing webhook produces a local connection problem; do not replace a webhook or take over another running integration automatically. Refuse simultaneous ownership of the same bot by another local Foldy watcher, including a watcher for a different root. A paired bot cannot be rebound until disconnected and paired again through a fresh local link.

**TG-03 — Disconnect and availability.** `telegram disconnect` or the paired user's Disconnect settings action invalidates the binding, outstanding pairing link, and old callback associations, and cancels undelivered messages for that binding. Stop starting sends immediately and abort in-flight requests where possible; already accepted Telegram messages cannot be recalled by disconnect. Preserve findings, corrections, pending questions, and locally accepted work. Local operation continues. Reconnecting requires a fresh local pairing link; old deliveries and old buttons are not reassigned to the new binding.

Processing incoming replies requires a running, connected watcher. Telegram retains incoming updates for at most 24 hours; Foldy cannot promise to recover messages sent during a longer outage. Keep pending questions locally without a timeout or guessed answer. `/status` can show current pending questions again after reconnection, with new associations where needed. Report a reply as accepted only after local persistence; the user's Telegram send indicator is not an acknowledgement from Foldy.

## 2. Results, questions, and feedback

**TG-04 — Useful messages.** Send a concise, user-facing result after useful work commits: a new meaningful finding, an applied organization result, or a generated artifact. Label partial results and actionable problems honestly. Unchanged/cached scans, repeated filesystem hints, no-op runs, and an unchanged error condition do not produce repeated announcements. A direct question or command still receives an answer when nothing changed. Result messages name the relevant files or subject and briefly explain the outcome; no generic scan dump, internal IDs, absolute state paths, raw errors, or hidden reasoning. Cite relevant source names and readable locations when answering questions without uploading their original files.

Only committed records authorize result delivery. Keep associations between each outgoing message and its actual result, finding, question, or artifact locally. If a result covers several targets, retain that set so later feedback can be disambiguated. Failed or abandoned work must not be described as completed. Once file delivery exists, use an attachment caption for a single generated file instead of adding a redundant completion message.

**TG-05 — Notification sound.** Settings offer All (default), Needs attention, and Silent. These modes select audible versus silent delivery, not whether messages or attachments exist. Needs attention alerts only for clarification questions and actionable problems; other results, replies, and attachments arrive silently. Silent requests silent delivery for everything. Use the current setting at send time, including retries. A result with several messages or attachments requests sound at most once; retries after uncertain delivery are silent. Telegram and device notification settings still govern presentation.

**TG-06 — Durable clarification.** The agent can invoke a narrow `request_clarification` tool with a nonempty question, suggested choices, and relevant work/source/finding context. Validate that referenced context belongs to the current root and run. The application assigns the request identity, persists the question and blocked work, and ends the current agent run at a safe boundary. Do not hold a model session or transaction open while awaiting a person, and do not execute later tools from the same proposed batch after the question stops the run. A question is pending work, not a completed result or a reason to repeatedly retry inference.

Present choices through CopilotKit's portable message/action/button components, rendered as Telegram single-select inline buttons, and include Something else, which opens a reply prompt for custom text. Register named components and serializable callback props so replies survive process restart. When meaningful alternatives do not exist, ask for a typed answer rather than inventing choices. Choosing Something else does not itself answer the question. A user may also reply directly to the question. Each prompt remains associated with its own pending request; an unrelated message is not implicitly the answer to the newest question. Multiple pending questions are supported. Only work dependent on a question waits; independent queued work may continue within the existing single-run limit.

**TG-07 — Answer and resume.** A request transitions from pending to answered or superseded. Accept an answer only for a pending request from the paired user or a targeted terminal command. Atomically save the answer, any targeted correction it establishes, and the continuation before acknowledging acceptance. Duplicate updates, repeated button clicks, and races between terminal and Telegram cannot create a second answer or continuation. Disable or remove answered buttons where possible; validate state even if editing the message fails.

Before accepting or using an answer, reconcile relevant source versions and applicable corrections. A source or intent change that invalidates the question supersedes it; explain that the situation changed and re-evaluate rather than applying a stale choice. Keep old questions and answers as history. Continue from current evidence in a fresh bounded run, respecting RUN-02 and all action preconditions. New accepted user input invalidates a cached reasoning result even when file bytes and model tag are unchanged. Answers received while paused are saved but their automatic continuations wait for resume. No answer expands file or external-action authority.

SDK callbacks and continuation tokens are handles to Foldy's persisted question, not the authority to resume work. Do not use a blocking `awaitChoice` or bypass Foldy's validation with an unconditional SDK resume. An expired SDK callback must leave the local question pending; status can publish fresh controls for it. Reconstruct a usable SDK conversation handle after restart instead of treating a previously serialized Thread or MessageRef object as a live capability.

**TG-08 — Feedback.** A reply to a result or generated attachment stays associated with that subject, not a new unrelated scan. Persist the received text and use CTX-05 when it supplies a correction. A question about the result receives a read-only contextual answer; a simple acknowledgement does not become a correction. If the result contains multiple plausible targets or the intended scope is unclear, present named choices before recording a scoped correction; retain the original feedback while asking. Acknowledgements describe the understood correction in ordinary language. A correction to one file does not become a folder-wide preference automatically, and changed sources do not make an old correction current again. A requested revision still uses normal planning and creation rules; it does not overwrite the earlier artifact.

Ordinary text outside an associated reply is a read-only question using current shared context. Incoming files, voice messages, edited messages, and forwarded copies without a valid local association do not silently become corrections, clarification answers, file imports, or executable commands. Explain unsupported input to the paired user with an appropriate supported next step. Never derive recipients, executable controls, or permission changes from source text or model prose.

## 3. Controls and persistence

**TG-09 — Shared controls.** CopilotKit message, command, and interaction handlers translate provider input into the same application operations used by the terminal. Keep handlers short: authorize, persist or enqueue, then return. Foldy's scheduler owns model runs and serial file operations. Configure SDK conversation admission explicitly and preserve ordered durable intake without holding pause/settings behind an entire model run or upload; the default parallel agent execution is not Foldy's execution policy. Observation continues while paused; pause is acknowledged only after any current mutation reaches the durable safe boundary. Read-only questions remain available while paused. Settings changes set a value rather than replaying a toggle. Telegram does not expose apply, undo, model selection, run-budget changes, root changes, or standing-instruction management menus.

| Telegram input | Behavior |
| --- | --- |
| `/start <pairing-secret>` | Pair only through TG-02; ordinary `/start` gives help to the paired user and no folder data to anybody else. |
| `/help` | Explain questions, contextual feedback, controls, and when the watcher must be running. |
| `/status` | Show understandable work/connection status and current pending questions; include a helpful delivery problem when present. |
| `/settings` | Show native buttons for pause/resume, notification mode, connection status, and Disconnect. |
| `/pause`, `/resume`, `/retry` | Use the corresponding existing work controls; retry does not answer a question or authorize an action. |
| Ordinary text | Ask a read-only question, unless explicitly replying to an associated question or result. |
| Reply or inline choice | Resolve the stored target and apply TG-07 or TG-08. |

Unknown commands explain the supported controls without being passed to the model as operational authority. Retry may requeue failed eligible deliveries as well as incomplete local work; it never recreates an already applied artifact. A transient delivery retry alone never schedules inference.

Terminal additions in T01 are `questions`, `answer <question-id> <text>`, `telegram pair`, `telegram status`, and `telegram disconnect`. `questions` and `answer` work without enabling Telegram. Internal identifiers may be shown in the terminal for these targeted controls; the chat must not require users to copy them. `correct folder <text>` remains a folder instruction, not an implicit answer to an arbitrary pending question.

**TG-10 — Durable state and ordering.** Extend the existing root-scoped SQLite database, preserving knowledge and schema validation through explicit migrations. Refuse an unsupported schema without resetting it. Keep received input, pending questions, accepted corrections/continuations, outgoing deliveries, and message associations independently of Pi session history. Supply a SQLite-backed implementation of CopilotKit's public StateStore contract for its callback/state needs; do not rely on its default MemoryStore. Reuse SDK normalization, rendering, and callback machinery rather than reproducing it in Foldy. Keep Foldy's domain records and outcome outbox authoritative; SDK queues or short deduplication TTLs do not replace durable acknowledgement and recovery requirements.

Persist each accepted Telegram update and the corresponding application command before allowing provider acknowledgement or sending an acceptance acknowledgement. Verify that the pinned direct adapter's ingress lifecycle allows this ordering; do not assume the managed gateway's guarantees apply. Deduplicate by provider, bot, and update identity across bindings; reconnecting the same bot must not reset its polling progress and replay old inputs. Settings changes and question answers must be idempotent; longer work is durably queued. Rejected/unsupported updates must not stall consumption of later valid updates. Check authorization before accepting input, and recheck the binding when executing queued connection/settings controls. Disconnect does not revoke ordinary work already accepted into the shared local scheduler, but prevents further execution of old connection controls or delivery to its chat.

No database transaction may span inference or Telegram network waits. T01 must replace the current scan-duration writer lock where necessary with process ownership independent of short transactions, while preserving scan rollback, knowledge integrity, root isolation, and overlapping-process refusal. Keep at most one active model run and serial file mutations. A crash while ingesting a reply, recording a correction, or scheduling a continuation must not lose acknowledged input or repeat a committed effect.

Minimum additional information, without prescribing a class hierarchy or SQL layout:

| Record | Information |
| --- | --- |
| Connection/settings | Root, SDK provider/conversation/actor identity, Telegram bot/user/chat identities, current binding identity, pairing verifier and expiry, sound preference; no service credentials |
| Clarification | Identity, originating work, question/choices, relevant targets and source versions, pending/answered/superseded state, accepted answer and continuation when present |
| Received command | Provider, binding, Telegram update identity, user text or validated control, target association, processing state; omit pairing secrets |
| Delivery | Unique logical outcome, provider and binding, user-facing message or committed artifact reference, attention class, delivery state, retry metadata, returned message association |
| SDK state | Namespaced serialized callback/component state and other StateStore facets required by the pinned SDK, backed by this SQLite database rather than a separate memory or cloud store |

**TG-11 — Delivery and failures.** Create outgoing delivery records with committed outcomes or reconcile them from those outcomes on recovery, using a unique logical key to close the crash gap between commit and enqueue. Deliver through the SDK to the stored authorized conversation, including outcomes produced without an incoming chat turn. Do not assume an SDK subscription flag implements proactive routing. Do not send speculative work or historical results from before the current pairing. A network failure never rolls back completed folder work. Retain pending deliveries through a watcher restart, use the SDK's transport/retry facilities where applicable, and retain Foldy's recovery responsibility for direct delivery. Coordinate retries so SDK and application retries do not independently repeat the same attempt; respect Telegram's `retry_after`. Bound requests and keep polling independent of uploads and model runs.

Permanent payload failures mark that delivery failed without blocking other eligible messages. Invalid Telegram or Intelligence credentials, bot blocking, or a competing poller produce an accurate local connection status; suspend affected delivery until usable. An Intelligence status intended for managed providers must not be mistaken for proof of direct Telegram readiness or failure. Avoid repeating a failure announcement for each retry. Before retrying, check the binding, current question state, notification preference, and artifact eligibility again. Superseded questions and disconnected bindings must not leak stale prompts or data through the queue.

Deduplicate known successful deliveries. Telegram sends have no application-level exactly-once guarantee: a crash or lost response after acceptance can cause a duplicate message on retry. Preserve all known returned message associations. Never treat such a duplicate as another action, correction, or resume. A reply to a message whose association was lost must ask the user to use the current question/result rather than guess its identity. Live acceptance must not claim exactly-once remote delivery.

## 4. Generated attachments and SDK integration

**TG-12 — Committed outputs only.** After T02, deliver each eligible newly generated file as an actual document attachment with a concise useful caption. The source of authority is an applied artifact-creation journal entry with its output path, expected fingerprint, and supporting context. Ordinary source files, moved input files, staging files, internal databases, and arbitrary model-supplied paths are not attachment candidates. Use the existing Markdown, text, and JSON output capabilities; this integration does not add file formats or generation tools.

Recover a missing delivery after an interrupted committed creation without repeating creation. Preserve the local artifact regardless of upload success. Message associations make feedback on an attachment target the originating artifact. A safe local undo after upload does not remove the copy already delivered in Telegram.

**TG-13 — Verify uploaded bytes.** Before every upload attempt, check that the journal entry remains applied, the artifact is current, and its supporting evidence and corrections remain applicable. Resolve and open the artifact within the root with the existing no-symlink containment protections. Verify the actual bytes to be uploaded against the recorded output fingerprint and upload those same bytes, avoiding a second path read after verification. Refuse missing, replaced, changed, undone, or stale artifacts. A source transition during queueing must not deliver an obsolete report as current. Preserve local files and give a useful explanation instead of substituting another file or content version.

Pass the verified bytes and filename to CopilotKit's `postFile` or its public direct Telegram file capability, which performs the document upload. Check its capability/result rather than assuming success. No URL-fetch or path-based upload shortcut is allowed. The documented current Telegram maximum is 50 MB per document. Apply the upload-size check before reading a larger body or sending it; an oversized artifact stays local and its message explains that it could not be attached. An upload failure must not trigger regeneration, deletion, overwrite, or an unbounded model retry. Telegram's attachment limit does not increase the core artifact-generation limits.

**TG-14 — CopilotKit boundary and later providers.** Use `@copilotkit/channels`, its `/telegram` and `/ui` entry points, and a compatible `@copilotkit/runtime`. Pin the verified package pair and lockfile when T01 begins. Create the Channel on CopilotRuntime and use the runtime's supported ready/status/stop lifecycle; do not invent a standalone `channel.start()` API. If a runtime mount needs an HTTP listener, bind it to loopback only. Keep the existing Pi/Ollama reasoning and Foldy tool allowlist, with the smallest in-process AG-UI bridge needed by the SDK. Do not replace Foldy's agent with a cloud-backed built-in agent or expose provider-supplied tools to it automatically.

The application configuration adds `FOLDY_COPILOTKIT_API_KEY` and `FOLDY_COPILOTKIT_CHANNEL_CODE` alongside the Telegram token. Use the configured CopilotKit Intelligence project and its normal hosted connection; self-hosting is not part of this slice. This dependency permits required channel/identity/lifecycle metadata and user-facing messaging/UI data, not automatic export of retrieved source content, raw Pi conversation/tool traces, database contents, or credentials. Disable optional Intelligence Memory and transcript export, keep SDK persistence local, and verify actual service traffic before claiming the data boundary. The direct Telegram connection does not by itself prove that the rest of the SDK sends no data to Intelligence. Missing integration configuration leaves local Foldy usable with a clear integration setup status.

Use CopilotKit's provider-neutral message/interaction types and portable components at the Foldy boundary. Include provider and conversation scope in binding, delivery, and SDK-state keys; a matching numeric actor or conversation ID from another provider is not the same identity. Register only Telegram now. Later providers reuse the same domain operations and SDK integration after their own identity, capability, file-delivery, and live checks; do not preconfigure credentials or silently enable every adapter exported by the package.

T01 starts by verifying the public SDK integration path for Pi, proactive delivery, safe input acknowledgement, persistent callbacks, notification sound, and service-data handling. T02 separately verifies actual file capability. Use supported lower-level provider APIs only for concrete capability gaps, keeping them inside the Channels integration; do not build a parallel hand-written transport. Record an unmet SDK capability as pending work rather than weakening a behavioral requirement or claiming it is covered by a mock.

## 5. Example conversations

These use synthetic subjects and describe observable behavior, not required wording.

| Step | Chat |
| --- | --- |
| Useful result | Foldy: “The hotel receipt and booking confirmation refer to the same Madrid stay.” |
| Clarification | Foldy: “Should this hotel receipt belong to the Madrid trip?” Buttons: Madrid trip / Keep separate / Something else. |
| Answer | User taps Keep separate. Foldy: “I'll keep this receipt separate.” The answer is saved before this acknowledgement. |
| Custom answer | User taps Something else, then replies “It belongs to the conference trip.” The reply resolves this question only. |
| Generated file | Foldy sends `September expenses.md` with “I prepared your September expense summary.” |
| Feedback | User replies to the file: “Exclude the Madrid hotel; it was personal.” Foldy records the targeted correction and schedules permitted re-evaluation. |
| Ambiguous feedback | User replies to a result covering two receipts: “That one is personal.” Foldy asks which receipt, with readable labels. |
| Settings | User selects Needs attention. The next result and its files arrive silently; a later clarification can alert. |
| Paused answer | User pauses and answers a question. Foldy confirms the saved answer and explains that the remaining work will continue after resume. |

Offline tests use temporary roots/state, scripted model outputs, controlled SDK/provider boundaries, and a controlled clock. They must reject real Telegram, Intelligence, and Ollama network access. Include checks against the installed SDK's public types, rendering, callback registration, and StateStore semantics; mocks alone cannot establish compatibility.
